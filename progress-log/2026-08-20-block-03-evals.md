# 2026-08-20 — Block 03: Evals and Non-Determinism

## What was done

- Built `dataset.json` with 4 hand-designed cases across 4 categories
  (clear-positive, negative, false-positive-trap, subtle-positive),
  anchored to real PR-review scenarios.
- Built `run-eval.ts`: calls the real Claude API with structured
  output (`tool_use`, forced tool choice), compares results against
  expected outcomes, prints a breakdown by category instead of a
  single accuracy number.
- Ran the eval multiple times, iterating on `reviewer-prompt.txt`
  based on real failures — not assumptions:
  - Round 1 (baseline): 1/4 (25%) — no severity rubric
  - Round 2 (added rubric + runtime-vs-types rule): 2/4 (50%) — fixed
    severity, but the new rule was too broad and created a new false
    positive on correct code
  - Round 3 (added a concrete few-shot example instead of a broader
    rule): 3/4 (75%), non-deterministic on `false-positive-trap`
  - Root cause found: the dataset itself had a type/logic mismatch,
    not the prompt. Fixed the type signature in the test case.
  - Confirmed with 3 consecutive runs: 4/4 (100%), consistent
    reasoning each time.
  - Added `temperature: 0` to reduce variability between runs,
    matching how this reviewer would run in production.
- Wrote `03-evals/README.md` documenting the full debugging process.

## Decisions made and why

- Prioritized fixing a real false positive (case-02, flagging correct
  code) over a data-classification issue (severity mismatch) — one
  creates noise on good code, the other is just miscalibration.
- Chose to widen the dataset's type signature (`number | undefined |
  null`) rather than narrow the code's null check, to keep the code
  defensive while removing the ambiguity that was confusing the
  model.
- Confirmed a passing result with 3 repeated runs before trusting it
  — a single pass on a non-deterministic system isn't proof of a fix.
